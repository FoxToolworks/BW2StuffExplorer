## 3. BWM model findings

### 3.1 Safe identity checks

All eight samples have this structure:

- bytes `0–39`: null-padded ASCII `LiOnHeAdMODEL`
- offset `40`: stored size equals actual file size minus 44 bytes
- offset `44`: magic number `0x2B00B1E5`
- offset `48`: format version `6`
- offset `124`: material-definition count
- offset `168`: vertex count
- offset `172`: stride count
- offset `176`: model type
- offset `180`: index count
- offset `184`: first 448-byte material definition

Observed model types:

- `type = 2`, one stride, no bones: static/articulated model
- `type = 3`, nine strides, non-zero bones: skinned model

The `binary_animations` samples still use BWM type 2. Their folder name should therefore be treated as context, not as a separate binary file format.

### 3.2 Material definition

Each material definition contains seven fixed 64-byte strings:

1. Diffuse texture
2. Light map
3. Growth map
4. Specular map
5. Animated texture
6. Normal map
7. Material/shader type

This lets the Explorer assign texture roles using direct model evidence rather than filename guesses.

### 3.3 Confirmed sample relationships

| Model | Texture reference | Slot | Result |
|---|---|---|---|
| `m_aztecabodea.bwm` | `t_aztec_building_abodes.dds` | Diffuse | Confirmed diffuse texture |
| `m_aztecabodea.bwm` | `t_aztec_building_abodes_spc.dds` | Specular | Confirmed specular map |
| `m_aztecabodea.bwm` | `t_aztecabodea_lod1_4_lightmap.dds` | Light | Confirmed light map |
| `m_aztectemple_uber.bwm` | `t_aztectemple_uber_1.dds` | Diffuse | Confirmed diffuse texture |
| `m_aztectemple_uber.bwm` | `t_aztectemple_uber_lod1_4_lightmap.dds` | Light | Confirmed light map |
| `m_greeksmelter.bwm` | `t_greek_smelter_neut_spc.dds` | Specular | Confirmed specular map |
| `m_aztec_tf_barrel01_n.bwm` | `t_aztec_urbanfurniture_n.dds` | Diffuse | `_n` is not a Normal Map marker here |

Across the eight samples, BWM parsing found:

- 10 distinct diffuse texture names
- 7 distinct light-map names
- 2 distinct specular-map names
- no populated growth, animated or normal slots in this limited sample
- 17 of 19 distinct role/name pairs resolve to actual `Everything.stuff` entries

Two BWM references are unresolved within `Everything.stuff`:

- `t_greek_prison_neut.dds`
- `t_aztectemple_uber_lod4_4_lightmap.dds`

The Explorer must retain unresolved references instead of silently discarding them. They may refer to loose root files, excluded assets or stale development data.

### 3.4 Important correction to name-based heuristics

`t_aztec_urbanfurniture_n.dds` is explicitly placed in the BWM diffuse slot. A rule such as “filename ending `_n` means Normal Map” would therefore produce a false classification. In this context `_n` likely means neutral alignment/state.

Recommended evidence priority:

1. Explicit BWM material slot
2. Other parsed asset reference
3. Strong path and filename rule
4. DDS technical properties
5. Generic `Texture` fallback

## 4. CAM structure

All three CAM samples satisfy:

```text
uint32 storedFileSize
uint32 timeOrScale
uint32 sampleCount
float32 channels[sampleCount][6]
```

Validation formula:

```text
actualFileSize == 12 + sampleCount × 24
storedFileSize == actualFileSize
```

Observed samples:

| File | Second field | Samples | Second field / samples |
|---|---:|---:|---:|
| `cam.cam` | 3,000 | 90 | 33.3333 |
| `flying.cam` | 60,000 | 1,800 | 33.3333 |
| `pathsymbol1.cam` | 3,333 | 499 | 6.6794 |

For the two normal camera files, the second field behaves exactly like duration in milliseconds at 30 samples per second. The path-symbol sample uses the same six-float record structure but a different relationship. v0.5 should expose `sampleCount` and the raw second field without yet naming it definitively for every CAM subtype.

## 5. EXC structure

Both samples start with the null-padded signature `LiOnHeAdcameraexc` and contain:

- a stored size equal to actual file size minus 44 bytes
- version `1`
- four currently unknown zero fields
- two `500.0` float values
- a 3D point count at offset 72
- `count × 3` float coordinates from offset 76
- an eight-byte footer

Observed point counts:

- `land1begin.exc`: 39 points
- `racetrack.exc`: 128 points

The signature, zone paths and coordinate arrays support the classification **Camera Exclusion Zone**. Footer semantics remain unknown.

## 6. RGB555 sky textures

Every `.555` sample is exactly 131,088 bytes:

```text
16-byte header
256 × 256 × 2-byte pixel data = 131,072 bytes
```

Header values are identical across the samples:

```text
0, 256, 256, 0x019D00B0
```

Decoding the payload as little-endian RGB555 produces a coherent sky image with the expected colors. RGB565 produces severe color banding and is not the correct interpretation.

Proposed v0.5 display:

```text
Class: Texture
Format: RGB555
Context: Weather / Sky
Dimensions: 256 × 256
Mipmaps: 1
```

The meaning of the fourth header value `0x019D00B0` remains unknown and should be preserved as a raw format marker.

## 7. Creature/advisor formats

### CSK

The CSK samples use `LiOnHeAdCreature` followed by a stable header tuple beginning with `12`, `4663`, `3`. They include:

- `geforce` and later `radeon` sections
- body/material names
- base texture names
- bump texture names
- morph names such as `base`, `evil`, `good`, `strong`, `thin`, `weak` and `young`

Proposed label: **Creature Skin/Morph Model**.

### CHA

The CHA samples use `LiOnHeAdCreature`, then values `4` and `9035`, followed by a `radeon` section and later a `hybrid` section. The structures and prior community reverse engineering identify CHA as creature hair/fur ribbon data that follows body morphs.

Proposed label: **Creature Hair/Fur Data**.

### CCS

CCS uses the same broad creature signature, but its first value after the 40-byte signature is a stored size equal to actual file size minus 44 bytes. It lacks the material and morph strings visible in CSK/CHA. Prior reverse engineering indicates that much of the format may be legacy data, with bounding information still used.

Proposed conservative label: **Creature Support/Bounding Data**. Do not call it a complete creature model in v0.5.

### ABN

`badvisor_evil.abn` begins with `LiOnHeAdhelpdude`, contains a stored size equal to file size minus 44 and version `1`. It contains 126 unique animation identifiers:

- 125 `.lhqa`
- 1 `.lhq`

Names include advisor gestures, emotions, scripted dialogue actions and screen positions. Proposed label: **Advisor Animation Bank**.

### Creature material references

CSK and CHA repeat material descriptors containing references such as:

- `T_ape.dds`
- `T_ape_bump.dds`
- `t_advisorevil.dds`
- `t_advisorevil_bump.dds`
- `T_hand.dds`
- `T_hand_bump.dds`
- `IncloudsCubemap.dds`

These formats can later provide additional evidence for Creature Diffuse, Creature Bump/Normal and Cubemap roles. Their full material record layout should be mapped before v0.5 assigns exact roles automatically.

## 8. DAN dialogue annotation packs

Both DAN samples begin with:

```text
LiOnHeAdAnnoPackFile
stored size = actual file size - 44
version = 1
marker = 0xFEEDBABE
```

Both contain exactly 2,100 unique `BW2T_SCRIPT_...` identifiers in the same order. File size differs by language, consistent with language-specific annotation/lip-sync payloads.

Proposed label: **Dialogue Annotation / Lip Sync Pack**.

## 9. BIK control sample

The sample begins with `BIKi`. Its stored size field equals actual file size minus eight bytes. It is a standard Bink video and requires no BW2-specific reverse engineering for v0.5.

## 10. Proposed v0.5 data model

Do not collapse everything into one display string internally. Store independent dimensions:

```text
Class       Texture, Model, Animation, Camera Data, Video...
Format      DDS, BWM, CSK, CHA, RGB555...
Subtype     Static Model, Skinned Model, Advisor Animation Bank...
Role        Diffuse, Light Map, Specular, Normal Map...
Context     Building, Creature, Landscape, UI, Weather...
Confidence  Confirmed, Probable, Generic
Evidence    Magic, Structure, BWM Slot, Path Rule, Name Rule...
```

Example:

```text
Class: Texture
Format: DDS
Role: Diffuse
Context: Aztec Building
Confidence: Confirmed
Evidence: Referenced by m_aztecabodea.bwm diffuse slot
```

## 11. Detector priority

1. Validate file bounds supplied by the STUFF entry.
2. Read only the minimum header required for identification.
3. Prefer strong magic/signature checks.
4. Apply structural invariants such as stored size and record counts.
5. Parse lightweight semantic references where the format is understood.
6. Resolve references case-insensitively against normalized archive paths and filenames.
7. Use path/name heuristics only when no stronger evidence exists.
8. Fall back safely to extension or `Unknown Binary`.

Malformed data must return an `Unknown` or invalid result; it must never crash archive browsing.

## 12. Recommended implementation order

### v0.5A – Format detector registry

- BWM, BIK, CAM, EXC, CSK, CHA, CCS, ABN, DAN and RGB555 detectors
- class, format, subtype, confidence and evidence model
- safe bounded reads only

### v0.5B – Lightweight BWM metadata reader

- header and model subtype
- material-definition table only
- diffuse/light/growth/specular/animated/normal references
- no geometry decoding required

### v0.5C – Archive relationship index

- case-insensitive filename/path lookup
- model-to-texture links
- reverse texture-to-model links
- unresolved-reference list
- strongest-evidence-wins role assignment

### v0.5D – Explorer presentation

- friendly type/group names
- optional role/context columns or properties
- appropriate icons
- search/filter over derived metadata

## 13. Full BWM corpus scan

**Scan package:** `BW2_BWM_Texture_Relationships_20260814_212905.zip`  
**Scope:** all 822 `.bwm` entries extracted from the retail `Everything.stuff` archive

### 13.1 Parser coverage

The confirmed BWM header and material-table parser successfully processed 820 of 822 files:

| Result | Files |
|---|---:|
| Parsed BWM files | 820 |
| Static/articulated models, type 2 with stride count 1 | 677 |
| Skinned models, type 3 with stride count 9 | 143 |
| Version 6 | 807 |
| Version 5 | 13 |
| Files without the expected BWM signature | 2 |

All 13 version-5 files retain the same validated size field, magic, material-table layout and model-type/stride relationship as version 6. They can therefore be parsed by the v0.5 metadata reader while preserving their version value.

The two extension/signature mismatches are:

- `data/art/models/m_aztec_altar.bwm` — 63,612 bytes
- `data/art/models/m_aztecbeautification_altar.bwm` — 93,268 bytes

Direct inspection of the original bytes confirms that both files are entirely zero-filled:

| File | Size | Non-zero bytes | Distinct byte values | SHA-256 |
|---|---:|---:|---:|---|
| `m_aztec_altar.bwm` | 63,612 | 0 | 1 (`0x00`) | `c8e6fa3e267fcf2702ea377952d326a707762285902e643dd8a8588cc70605c6` |
| `m_aztecbeautification_altar.bwm` | 93,268 | 0 | 1 (`0x00`) | `e351f21532aae9aaaf5f442cafdf4510eb896092d581ab9fe5f283442b1cc597` |

They contain no hidden signature, compressed stream, embedded name or partial model data. They are therefore confirmed empty/dummy model resources rather than an undocumented BWM variant. The v0.5 detector should label this exact structural case **Empty/Placeholder Model (BWM)** and must not invoke the normal material parser. A non-zero `.bwm` without the expected signature remains **Unknown Model Data (BWM)**.

Directory and subtype correlation is exact for the parsed corpus:

- `data/art/models`: 452 static/articulated models plus the two signature mismatches
- `data/art/features`: 223 static/articulated models
- `data/art/skins`: 143 skinned models
- `data/art/binary_animations`: 2 static/articulated BWM models

This confirms that binary structure, not directory name, should determine the displayed BWM subtype.

### 13.5 Impact on the existing Phase-3 inventory

Cross-referencing the 1,271 resolved DDS paths against `BW2_Asset_Inventory_Phase3.csv` shows:

- all 646 resolved BWM Light Maps were already classified as `Lightmap`
- 81 resolved BWM Specular Maps were already classified as `Specular`
- one resolved Diffuse Map was already classified as `Diffuse`
- 542 model-referenced DDS files were still `Unklassifiziert`

The BWM relationship index safely adds evidence for the previously unclassified set, including:

- 484 files used in a Diffuse slot
- 32 files used in a Specular slot
- 17 files used in a Growth slot
- 10 files used in an Animated slot
- 6 files used in a Normal slot

Counts overlap where a texture has multiple confirmed roles. This result validates the conservative Phase-3 approach: it avoided false guesses and left exactly the assets that can now be classified from stronger model evidence.

### 13.6 Revised v0.5 implementation rules

1. Accept both observed BWM versions 5 and 6 after signature, size, magic and material-bounds validation.
2. Determine static/articulated versus skinned subtype from the binary model type; use the folder only as context.
3. Build a case-insensitive archive-wide DDS filename/path index before resolving BWM references.
4. Preserve unresolved and ambiguous references as first-class relationship results.
5. Store zero or more confirmed roles per texture; do not force a single-role database model.
6. Give explicit BWM-slot evidence priority over filename, path and DDS-property heuristics.
7. Never infer a missing DDS through fuzzy similarity automatically.
8. Fall back safely when a `.bwm` entry lacks the expected signature or violates bounds.
9. Keep the Explorer's existing compact Type column; friendly output can combine the strongest classification with the technical extension, for example `Specular Map (DDS)` or `Skinned Model (BWM)`.
10. Detect a non-empty, entirely zero-filled `.bwm` as `Empty/Placeholder Model (BWM)`; reserve `Unknown Model Data (BWM)` for non-zero signature mismatches.

## 14. Research conclusion and code handoff

The full BWM scan is complete and provides sufficient evidence to implement the v0.5 detector registry, BWM metadata reader and archive relationship index.

The final narrow format question is resolved: both signature mismatches are confirmed zero-filled placeholder resources. No unexplained BWM variant remains in the retail `Everything.stuff` corpus. The BWM research phase is complete.

Recommended implementation sequence:

1. Add the classification result/evidence model and detector registry.
2. Add safe extension-plus-signature detectors for the 13 known archive formats.
3. Implement the bounded BWM v5/v6 material reader.
4. Build model-to-texture and reverse texture-to-model indexes after archive load.
5. Derive the compact Type-column display text without changing the existing column layout.
6. Add tests for normal, version-5, ambiguous-reference, missing-reference, multi-role, zero-filled-placeholder and non-zero-signature-mismatch cases.
