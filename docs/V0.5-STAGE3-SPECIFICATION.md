# Version 0.5 Stage 3 — File Details and References

## Stage 3.1 scope

Stage 3.1 restructures entry properties into three tabs:

- **General** retains name, archive path, friendly type, modification time, size and offset;
- **File details** shows factual, format-specific metadata;
- **References** hosts the separate, scrollable Stage 3.2 relationship table.

No empty Preview tab is displayed. The properties layout and metadata model leave room for a future Preview tab to become the first and initially selected tab once an actual viewer exists.

Stage 3.1 specializes DDS only. Other formats show their known format and a neutral message that no specialized metadata reader is available. Modding recommendations are intentionally excluded.

Stage 3.1.1 retains this layout and adds a second, independent alpha fact derived from compressed DDS payload data.

Stage 3.2 adds factual BWM details and turns the References surface into a bidirectional BWM/DDS relationship table.

Stage 3.3 moves DDS, BWM and fallback inspection behind one shared metadata-provider service. This is an architecture-only stage: the three visible tabs and their values remain unchanged.

## Stage 3.3 shared inspection system

The properties window no longer chooses a parser from file extensions. It creates one `Bw2AssetInspectionContext`, asks `Bw2AssetInspectionService` for a result and only formats that result for display.

Each `IBw2AssetMetadataProvider` can return:

- a shared `Valid`, `Invalid` or `Unsupported` inspection state with an error reason when invalid;
- typed, factual file-detail fields;
- a model-to-texture, texture-to-model or unavailable reference view;
- the corresponding relationships and honest empty-state reason;
- an optional preview descriptor containing a preview kind and viewer identifier.

The built-in provider order is DDS, BWM and a final neutral fallback. Additional providers can be registered ahead of the built-ins without changing the properties window. No built-in provider returns a preview descriptor in Stage 3.3, so no Preview tab is displayed.

Asset bytes are accessed through `IBw2AssetSource`, not through a hard dependency on `StuffArchive`. `StuffArchiveAssetSource` adapts a bounded archive entry, while `LooseFileAssetSource` adapts a normal file and may carry a separate logical BW2 path. DDS and BWM inspection therefore already works for either source. Archive-wide classifications and relationships remain optional context supplied separately; inspecting a loose file never invents relationships that a root index has not proven.

The BWM reader consequently supports a neutral stream, declared length and extension in addition to its compatibility overload for STUFF entries. This separation is the base for a later root index that can combine archive entries, loose assets and other archives before resolving cross-file relationships.

## Bounded DDS parsing

The reader opens the selected archive entry through its bounded `StuffEntryStream`. It reads exactly:

- 128 bytes for the magic plus legacy `DDS_HEADER`; and
- an additional 20 bytes only when the FourCC is `DX10`.

The header reader does not decode pixels, read mip payloads or create a preview. A truncated entry, invalid magic, invalid 124-byte header size, invalid 32-byte pixel-format size, zero dimensions or incomplete/invalid DX10 extension produces an `Invalid` result with a reason rather than an exception in the UI.

## Stage 3.1.1 compressed alpha analysis

After a valid header has been read, a separate scanner can inspect the compressed payload for BC1, BC2 and BC3 formats. Classic `DXT1`, `DXT2`/`DXT3` and `DXT4`/`DXT5` FourCC values and the corresponding DX10 BC1/BC2/BC3 format variants use the same block rules.

The scanner:

- verifies that the declared mip/subresource payload is present before reporting a result;
- checks every declared mip level and every declared array element, cubemap face or volume slice;
- ignores encoded padding texels outside the valid width and height of partial 4 × 4 edge blocks;
- allocates no decoded image and stops after the first valid non-opaque pixel;
- reports `Unknown` for truncated data, unsupported alpha-capable formats or invalid subresource layouts.

BC1 counts selector 3 as transparent only when the block is in its three-color/transparent mode. BC2 checks the explicit four-bit alpha value selected by each valid pixel. BC3 reconstructs the block's eight-entry alpha palette and checks the value selected by each valid pixel.

## Displayed DDS facts

Depending on the header, File details can show:

- dimensions and declared depth for a volume texture;
- legacy or DX10-extended header kind;
- 1D, 2D, 3D, array or cubemap resource kind;
- normalized block-compression family and original FourCC;
- exact recognized DXGI format and numeric value;
- effective mip-level count, where a zero legacy field still implies the required base image level;
- pitch or linear-size field when its corresponding DDS flag is set;
- DX10 array size;
- number of legacy cubemap face flags declared;
- color-space declaration when provable;
- whether the declared pixel format is capable of carrying alpha;
- whether supported compressed payload data contains at least one valid non-opaque alpha value.

`Alpha-capable format` is deliberately not a claim that the texture contains meaningful alpha pixels. `Non-opaque alpha data` answers only whether the stored supported payload contains a value below full opacity; it does not claim that a game material or shader uses that channel.

The displayed states are:

- `Yes` when at least one valid non-opaque alpha value is proven;
- `No` when the complete supported payload was checked and every valid alpha value is fully opaque;
- `Not applicable` when the declared format cannot carry alpha;
- `Unknown` when the fact cannot be proven safely.

## Stage 3.2 BWM details

A valid BWM version 5 or 6 displays:

- the `LiOnHeAdMODEL` signature and `0x2B00B1E5` magic value;
- the stored BWM version;
- the numeric model type together with the recognized static (`2`) or skinned (`3`) meaning;
- the declared material count;
- the number of non-empty texture-reference slots across all materials.

The bounded BWM reader validates entry size, signature, stored payload size, magic, version and material-table bounds. Invalid or unsupported data shows an `Invalid` header state with the concrete failed check. Geometry is not decoded.

Each texture reference retains its zero-based material index, material-slot role and original stored path. The six confirmed slots are diffuse, light, growth, specular, animated and normal.

## Stage 3.2 References table

For a selected BWM, each row shows:

- zero-based material index;
- material-slot role;
- original stored texture reference;
- resolution status;
- resolved DDS archive path, all ambiguous candidates, or no target for a missing reference.

For a selected DDS, the same table is reversed and shows the BWM entry, material index, role, stored reference and resolution status. A DDS that is one of several filename candidates is included only with the explicit `Ambiguous` status; it is never presented as a confirmed use.

The resolution states are:

- `Resolved — exact path` for one normalized archive-path match;
- `Resolved — unique filename` when no exact path matched and one DDS filename is unique archive-wide;
- `Missing` when no candidate exists;
- `Ambiguous` when multiple candidates remain.

Landscape and creature filename-family roles do not create reference rows because they are semantic classifications, not stored BWM references. Other file formats retain a neutral message until a specialized relationship provider exists. The table scrolls independently when its rows or columns exceed the available space.

## Color-space rule

Classic FourCC formats such as DXT1, DXT3 and DXT5 do not declare sRGB versus linear interpretation in the legacy DDS header. They therefore display:

```text
Color space: Unknown
```

For a valid DX10 extension, recognized explicit `*_UNORM_SRGB` variants display `sRGB`; recognized corresponding non-sRGB UNORM variants display `Linear`. Typeless formats and formats without an explicit relevant distinction remain `Unknown`.

Semantic texture roles, filenames and modding rules never overwrite the header-derived color-space value. No recommendation is displayed in Stage 3.
