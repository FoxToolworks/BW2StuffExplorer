# Version 0.5 Stage 2 — BWM and DDS Relationship Analysis

## Scope

Stage 2 adds content-aware BWM classification and DDS roles confirmed by BWM material references. The analysis is read-only, runs once on a background thread while the archive opens and stores its metadata before the file list is shown. Scrolling, sorting and grouping do not parse file payloads.

Stage 2.1 keeps grouped large-folder views responsive by explicitly enabling WPF row and column virtualization, recycling and virtualization while grouping. Incremental search uses a cancellable 450 ms debounce, and a lone punctuation character such as `.` remains pending rather than rebuilding a result set containing nearly the entire archive.

Stage 2.2 adds conservative filename-family evidence for DDS entries below the confirmed landscape and creature roots. Asset context is stored separately from the displayed file type, so the existing file-type grouping remains compact.

Stage 2.3 makes file type and semantic usage fully independent. Every DDS is displayed as `Texture (DDS)`, while its zero, one or multiple detected roles remain stored for the planned File details tab and an optional future `Group by → Texture role` view.

## BWM validation

A BWM payload is parsed only when all of these checks succeed:

- entry size is at least the confirmed 184-byte header;
- the null-terminated header signature is `LiOnHeAdMODEL`;
- the stored payload size equals the STUFF entry length minus 44 bytes;
- the magic value is `0x2B00B1E5`;
- the version is one of the observed compatible versions 5 or 6;
- `184 + materialCount × 448` stays within the bounded STUFF entry.

The reader then reads only the fixed material table. Geometry, vertices, indices, bones and animation data are not decoded.

| Binary result | Displayed file type |
| --- | --- |
| Valid model type 2 | Static Model (BWM) |
| Valid model type 3 | Skinned Model (BWM) |
| Invalid header, unknown model type or any failed invariant | Unknown Model Data (BWM) |

The two known zero-filled altar entries intentionally use the same unknown fallback as every other unreadable BWM payload.

## BWM material slots

Each confirmed 448-byte material contains six fixed 64-byte texture-reference slots:

| Material offset | Confirmed role |
| ---: | --- |
| 0 | Diffuse Map |
| 64 | Light Map |
| 128 | Growth Map |
| 192 | Specular Map |
| 256 | Animated Map |
| 320 | Normal Map |

Empty slots are ignored. Non-empty references are preserved as relationship records even when no DDS can be selected.

## Reference resolution

Resolution is case-insensitive and uses this evidence order:

1. normalized archive-relative path;
2. the same path with a leading `data/` when absent;
3. a filename match only when exactly one DDS entry has that filename;
4. missing or ambiguous result without fuzzy matching.

An ambiguous reference retains every candidate and does not classify any candidate DDS. A missing reference also remains a first-class relationship result. This prevents development-time names and duplicate filenames from becoming false facts.

## DDS file type and detected roles

| Confirmed relationship result | Displayed file type | Stored role metadata |
| --- | --- | --- |
| No uniquely resolved BWM role | Texture (DDS) | None unless a safe family rule matches |
| Exactly one role | Texture (DDS) | The confirmed role |
| More than one role | Texture (DDS) | Every confirmed role |

The Type column therefore answers what the file is, not how the game uses it. Role metadata answers the second question without fragmenting normal Explorer-style file-type grouping.

## Landscape and creature texture families

BWM material evidence always has priority. Only a DDS without a uniquely resolved BWM role is considered for the following exact path-and-filename rules; there is no fuzzy or substring-only classification.

| Required archive root | Exact filename ending or name | Stored detected role |
| --- | --- | --- |
| `data/landscape/` | `_dif.dds` | Diffuse Map |
| `data/landscape/` | `_baked.dds` | Baked Texture |
| `data/landscape/` | `_nrm.dds` | Normal Map |
| `data/ctr/` | `_d.dds` | Diffuse Map |
| `data/ctr/` | `_b.dds` | Normal Map |
| `data/ctr/` | `_s.dds` | Specular Map |
| `data/ctr/` | `scalebias.dds` ending | Scale/Bias Map |
| `data/ctr/` | exact name `t_strand.dds` | Fur/Strand Texture |

Every matched or unmatched DDS remains `Texture (DDS)`. An unmatched file has no detected role, but its landscape or creature context is still retained internally. A BWM-referenced DDS outside both families receives model context; a BWM-referenced DDS inside a family retains that more specific family context. Neither context nor role is appended to the Type value.

Names such as `normalize.dds` and `incloudscubemap.dds` do not receive speculative cubemap or normal-map types from their names. Factual DDS header metadata belongs to Stage 3.

## Retail-corpus expectations

The separately verified retail scan establishes these expected results for `Everything.stuff`:

- 820 valid BWM entries: 677 static and 143 skinned;
- 2 invalid, zero-filled BWM entries;
- 3,396 non-empty material-slot uses;
- 3,266 uniquely resolved uses, 126 missing uses and 4 ambiguous uses;
- 1,271 DDS files with at least one confirmed BWM role;
- 6 DDS files with multiple confirmed roles.

The verified family scan additionally establishes 272 DDS entries below `data/landscape/` (91 diffuse, 80 baked, 82 normal and 19 unmatched) and 88 below `data/ctr/` (23 diffuse, 23 normal/bump, 23 specular, 12 scale/bias, 5 strand and 2 unmatched before BWM precedence).

The integrated resolver was cross-checked against the complete archive inventory and relationship CSVs and reproduces these relationship totals.

The analysis operates on the archive currently opened rather than on a hard-coded retail-file list. A future writer can rerun the same analysis after inserting or replacing files; a valid imported BWM can therefore provide roles for its DDS references when they resolve uniquely.
